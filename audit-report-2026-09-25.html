1 — Executive summary & verdict

What this is: TeamFlow — a multi-tenant SaaS (Linear + Jira + Slack-lite) built as a pnpm + Bun + Turbo monorepo. Hono modular-monolith API with Postgres RLS + Redis + BullMQ + WS realtime; Next.js 16 / React 19 frontend with Tailwind 4 + Base-UI + framer-motion; thorough docs/design suite (8 docs + SVG architecture).

What's good: genuinely strong tenant-isolation design (composite (tenant_id,id) PKs + SET LOCAL app.tenant_id + RLS fail-closed + NOSUPERUSER role); clean modular backend (modules/*, lib/*, zod + jose, stable error envelope); strict TypeScript base (strict + noUncheckedIndexedAccess + isolatedModules + moduleDetection:force); economy of tooling (Turbo + shared configs); excellent design-doc depth for a v0.

What's risky: secrets hygiene (committed keys), prod-readiness gaps (no CI, no Dockerfile, no prod logger/metrics, backend has no ESLint), dual ORM + dual package-manager drift, Supabase CLI scaffold is dead while frontend points at a live hosted project, design-doc numbers drift (2.5k vs 10k vs 30k vs 50k DAU), port mismatches (:3000 vs :4000 vs :4002 vs :3001 in docs), orphan apps/web stub.

5 — Database, migrations & Supabase

5.1 Postgres (source of truth: backend, not Supabase CLI)

  • Engine: PG 16-alpine via apps/backend/docker-compose.yml (:5432) + docker/init.sql creating NOSUPERUSER teamflow so RLS applies. Supabase CLI declares PG 17 — version skew to reconcile.
  • Migrations: 0001_init → 0010_chat_realtime via bun src/db/migrate.ts using sql.unsafe(fileBody).simple() — safe (local files only) provided image build pins migration hashes.
  • Model: 20+ tables per docs/design/data-model.md; tenant tables keyed (tenant_id,id) with tenant-carrying FKs — cross-tenant refs impossible by constraint. Cursor pagination, soft-delete, tsvector+GIN FTS.
  • RLS: fail-closed policies on app.tenant_id; no context → zero rows / rejected writes. Design + backend README agree. data-model.md still sketches app.current_user_id + organization_id — update to app.tenant_id.

5.2 Supabase local scaffold — effectively dead

supabase/config.toml (415 lines, stock): project_id=taskChecker, api :54321, db :54322/shadow :54320, pooler disabled, studio :54323, smtp :54324, storage 50MiB+s3+vector, realtime on, analytics :54327, auth signup-on/JWT-3600. But: no migrations/, no seed.sql (despite seed.sql_paths enabled), no functions/. .temp/ holds only cli-latest v2.117.0. Live linkage exists only via env examples pointing at hosted lnplireboawtrfpwpcdd.supabase.co.

Recommendation: either (A) adopt Supabase properly (move migrations under supabase/migrations, add seed.sql, enable pooler, document env) or (B) delete supabase/ scaffold and standardize on compose+Drizzle. Hybrid confusion is the current worst option.

5.3 ORM duality

Both drizzle-orm 0.44 + postgres 3.4 (runtime) and @prisma/client 6.4.1 + prisma 6.4.1 (scripts prisma:generate|migrate|studio unused in practice) are installed. Cost: migration drift, double schema source, larger image. Recommendation: keep Drizzle; remove Prisma deps/scripts or isolate todocs tooling.
